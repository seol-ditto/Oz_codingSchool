# 브랜치 전략
- **여러 개발자가 하나의 저장소를 사용하는 환경**에서 저장소를 효과적으로 활용하기 위한 work-flow
- 브랜치의 생성, 삭제, 병합 등으로 협업에서 혼란을 최대한 줄이고 소스를 관리할 수 있도록

> 만약 브랜치 전략을 사용하지 않는다면?
- 어떤 브랜치가 가장 최신의 내용을 담고 있지?
- 어디에 내 작업물을 push해야하지?
- 새로운 작업을 시작할 때 어느 브랜치의 내용을 가져와야하지?

등의 혼란을 경험할 수 있다.

프로젝트를 진행할 때 코드 버전 관리를 위해 주로 Git과 GitHub를 사용하게 되는데 Git branch 전략은 대표적으로 두 가지가 있다.
| 전략 | 내용 |
| --- | --- |
| Git Flow | 제품 출시 버전, 개발 버전, 기능, 출시 준비, 버그 수정 등 다양한 branch 관리 |
| GitHub Flow | 하나의 기본 브랜치(**main**)과 여기에 기능을 추가하기 위한 브랜치(**feat** 등) **두 개**만으로 운영 |

이 중 먼저 GitHub Flow에 대해서 알아보았다. 

## GitHub Flow
- 하나의 기본 브랜치인 `main` 브랜치는 항상 최신 상태
- 기능 개발, 수정 등 어떤 이유로든 새로운 브랜치 생성해서 작업 진행(항상 `main` 브랜치에서 생성!!)
    - 이 때 브랜치의 이름은 의도를 명확하게 알 수 있도록 설정
        - `feat/user-login`
        - `fix/date-format-error`
        - `docs/git-flow-summary`
### GitHub Flow 흐름
1. 브랜치 생성
2. 개발을 진행하면서 commit 남기기
    - 이 때도 브랜치 이름처럼 명확하게 내용을 파악할 수 있도록 작성
3. 원격 레포지토리로 수시로 push(다른 사람들이 내용을 확인할 수 있도록)
4. PR(Pull Request) 생성
    - 피드백이나 도움이 필요할 때
    - merge 준비가 완료되었을 때
    - merge하게되면 바로 main 브랜치에 합쳐져 배포되기 때문에 merge 전 팀원간의 상세한 리뷰가 필요함
5. 테스트
    - 리뷰가 완료되었다면 최종 merge 전 라이브 서버 등에 테스트 배포
    - 문제가 발견되었다면 바로 `main`의 내용으로 재배포해서 초기화(테스트 내용 덮어씌우기)
6. 최종 merge
    - 문제가 없다면 그대로 `main` 브랜치로 push(=배포)


## Git Flow
- 기본적인 브랜치 구분
    - `main` : 라이브 서버에 제품으로 출시되는 브랜치
    - `hotfix` : `main` 브랜치에서 발생한 버그를 수정하는 브랜치
    - `release` : 다음 버전 출시를 준비하는 브랜치.
        - `develop` 브랜치를 `release` 브랜치로 옮기고 QA, 테스트 진행 후 `main` 브랜치로 merge
    - `develop` : 다음 출시 버전을 대비하여 개발하는 브랜치
    - `feature` : 추가 기능 개발 브랜치
        - 모든 내용을 `develop` 브랜치로 merge
