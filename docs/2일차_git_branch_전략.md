# Git Flow와 GitHub Flow 브랜치 전략 정리

- **목적:** 팀 프로젝트의 Git/GitHub 협업 방식을 이해하기 위해 대표적인 브랜치 전략인 Git Flow와 GitHub Flow를 함께 공부하고 정리한다.

> 한 줄 요약
> - **Git Flow** = 개발 → 테스트 → 출시처럼 여러 단계로 나눠 꼼꼼하게 출시하는 방식
> - **GitHub Flow** = 내가 만들고 → 확인받고 → `main`에 바로 합치는 방식

---

## 1. Git 브랜치 전략이란?

### 1.1 브랜치(Branch)

브랜치는 **기존 코드에 영향을 주지 않고 독립적으로 작업하기 위한 작업 공간**이다. 원본 문서를 복사해 만든 작업용 사본과 비슷하며, 작업이 끝나면 변경 내용을 원래 브랜치에 병합(Merge)한다.

### 1.2 브랜치 전략

브랜치 전략은 여러 개발자가 하나의 저장소(Repository)에서 협업할 때 **브랜치를 어디서 만들고, 어떤 이름을 붙이고, 언제 어디로 병합할지** 정해 둔 팀의 공통 규칙(Workflow)이다.

만약 브랜치 전략이 없다면 다음과 같은 혼란을 겪을 수 있다.

- 어떤 브랜치가 가장 최신 내용을 담고 있지?
- 내 작업물은 어디에 push해야 하지?
- 새 작업을 시작할 때 어느 브랜치의 내용을 가져와야 하지?

| 필요한 이유 | 설명 |
|---|---|
| 동시 작업 | 기능별 브랜치에서 작업하므로 서로의 작업에 영향을 주지 않는다. |
| 충돌 최소화 | 작업 범위가 나뉘어 Merge Conflict가 줄어든다. |
| 작업 추적 | 브랜치가 기능·이슈 단위로 나뉘어 변경 이력을 파악하기 쉽다. |
| 안정성 | 배포용 브랜치에는 검토를 거친 코드만 반영되고, 문제 시 롤백이 쉽다. |
| 코드 리뷰 | 병합 전에 Pull Request로 팀원의 검토를 받을 수 있다. |

대표적인 전략은 다음 두 가지다.

| 전략 | 내용 |
|---|---|
| Git Flow | 출시 버전, 개발 버전, 기능, 출시 준비, 버그 수정 등 역할별로 여러 브랜치를 관리 |
| GitHub Flow | 하나의 기본 브랜치(`main`)와 작업 브랜치, 두 종류만으로 운영 |

## 2. Git Flow

### 2.1 정의와 특징

Git Flow는 2010년 Vincent Driessen이 제안한 브랜치 모델이다. 역할이 정해진 여러 브랜치를 사용해 **개발, 출시 준비, 긴급 수정을 분리**하고, 버전 단위의 체계적인 릴리스 관리를 목표로 한다.

**비유: 팀으로 그림책 만들기**

- 팀원 1은 그림, 팀원 2는 이야기, 팀원 3은 오타 수정, 팀원 4는 완성본 확인을 맡는다.
- 그림을 그리자마자 완성된 책에 바로 넣으면 문제가 생길 수 있으므로, **단계별로 확인**한 뒤 출간한다.

### 2.2 브랜치별 역할

| 브랜치 | 생성 위치 | 병합 대상 | 역할 | 그림책 비유 |
|---|---|---|---|---|
| `main` | - | - | 배포된 최종 제품 상태를 보관 | 정식으로 출간한 책 |
| `develop` | `main` | `release`를 거쳐 `main` | 다음 출시를 위해 기능을 통합 | 다음 책을 준비하는 곳 |
| `feature/*` | `develop` | `develop` | 새로운 기능 개발 | 각자 새 그림·이야기를 만드는 공간 |
| `release/*` | `develop` | `main`, `develop` | 출시 전 QA·테스트와 버그 수정 | 출간 전 최종 점검 |
| `hotfix/*` | `main` | `main`, `develop` | 배포 후 발견된 긴급 버그 수정 | 출간된 책의 긴급 수리 |

`main`과 `develop`은 계속 유지되는 브랜치이고, 나머지는 필요할 때 만들었다가 병합 후 삭제한다.

### 2.3 개발 및 배포 흐름

```text
develop ──▶ feature/기능 ──(PR·리뷰)──▶ develop
develop ──▶ release/버전 ──(테스트·수정)──▶ main(배포, 버전 태그) + develop
main    ──▶ hotfix/버전  ──(긴급 수정)──▶ main + develop
```

1. `develop`에서 `feature` 브랜치를 만들어 기능을 개발한다.
2. 완료된 기능은 Pull Request와 리뷰를 거쳐 `develop`에 병합한다.
3. 출시할 기능이 모이면 `develop`에서 `release` 브랜치를 만들어 테스트하고 버그를 수정한다.
4. 테스트가 끝나면 `release`를 `main`에 병합해 배포하고, 같은 내용을 `develop`에도 병합한다.
5. 배포 후 긴급 버그가 생기면 `main`에서 `hotfix`를 만들어 수정하고 `main`과 `develop`에 모두 반영한다.

### 2.4 장단점

| 장점 | 단점 |
|---|---|
| 브랜치 역할이 명확해 대규모 협업에 적합 | 브랜치 종류가 많아 구조가 복잡 |
| `release`, `hotfix`를 통한 명확한 배포 절차 | 병합 경로가 많아 관리 부담이 큼 |
| 버전 관리와 롤백이 체계적 | 수시로 빠르게 배포해야 하는 환경에는 무거움 |

## 3. GitHub Flow

### 3.1 정의와 특징

GitHub Flow는 GitHub에서 제안한 **단순한 브랜치 기반 작업 흐름**이다. 항상 배포 가능한 `main` 브랜치 하나와 짧게 쓰고 지우는 작업 브랜치로 운영하며, **Pull Request와 코드 리뷰**를 중심으로 협업한다. 자주 배포하는 웹 서비스처럼 빠른 개발과 피드백이 중요한 환경에 적합하다.

**비유: 그림책에 고양이 그림 추가하기**

1. `main`에서 새 작업 공간 `add-cat`을 만든다.
2. 그 공간에서 고양이를 그린다.
3. 다 그렸으면 PR을 만들어 팀원에게 보여준다.
4. 팀원이 확인하고 문제가 없으면 `main`에 합친다.
5. 수정된 그림책을 공개한다.

### 3.2 main과 작업 브랜치

| 브랜치 | 역할 |
|---|---|
| `main` | 항상 최신이자 배포 가능한 상태를 유지한다. 직접 작업하지 않고 PR을 통해서만 변경한다. |
| 작업 브랜치 | **항상 `main`에서 생성**하며 하나의 기능이나 수정 작업을 담당한다. 병합 후 삭제한다. |

`develop`, `release`, `hotfix` 같은 별도 브랜치를 반드시 만들 필요가 없다.

### 3.3 브랜치 이름 짓기

브랜치 이름만 보고도 **무엇을 하는 작업인지** 알 수 있도록 `종류/하는-일` 형태로 짓는다.

| 접두어 | 용도 | 예시 |
|---|---|---|
| `feat/` | 새 기능 추가 | `feat/user-login` |
| `fix/` | 버그 수정 | `fix/date-format-error` |
| `docs/` | 문서 작업 | `docs/git-flow-summary` |
| `refactor/` | 동작은 그대로 두고 코드 구조 정리 | `refactor/split-user-service` |
| `chore/` | 설정·잡무 | `chore/update-gitignore` |

`name`, `test2`처럼 사람 이름이나 의미 없는 이름은 "누가" 작업하는지만 보이고 "무엇을" 하는지는 드러나지 않으므로 피한다. 커밋 메시지도 같은 원칙으로 내용을 명확하게 작성한다.

### 3.4 작업 흐름

```text
Branch → Commit → Push → Pull Request → Review → (Test) → Merge
```

| 단계 | 내용 |
|---|---|
| Branch | 최신 `main`에서 작업 내용이 드러나는 이름으로 브랜치 생성 |
| Commit | 의미 있는 단위로 변경 사항 기록 |
| Push | 다른 사람이 확인할 수 있도록 작업 브랜치를 원격 저장소에 수시로 업로드 |
| Pull Request | 피드백이 필요하거나 병합 준비가 되었을 때 `main` 병합 요청을 생성하고 변경 내용 설명 |
| Review | 병합 즉시 `main`에 반영되므로 상세한 리뷰가 중요. 수정 요청은 같은 브랜치에 커밋·푸시하면 PR에 자동 반영 |
| Test | 필요하면 병합 전에 테스트 서버 등에 배포해 확인. 문제가 생기면 `main` 내용으로 다시 배포해 되돌림 |
| Merge | 승인 후 `main`에 병합(=배포 가능한 상태)하고 작업 브랜치 삭제 |

### 3.5 Pull Request의 base와 compare

```text
base: main  ←  compare: feat/login
(병합될 대상 브랜치)   (변경 내용을 가진 브랜치)
```

PR은 **compare 브랜치의 변경 내용을 base 브랜치로 병합**하는 요청이다. GitHub는 PR을 만들 때 base를 저장소의 기본 브랜치로 자동 지정하므로, 의도한 브랜치가 맞는지 꼭 확인해야 한다.

### 3.6 장단점

| 장점 | 단점 |
|---|---|
| 구조가 단순해 배우고 적용하기 쉬움 | 별도의 릴리스 브랜치가 없어 버전 단위 관리가 어려움 |
| PR 중심이라 코드 리뷰가 자연스럽게 이루어짐 | 여러 버전을 동시에 유지보수하기 어려움 |
| 작게 자주 병합하므로 빠른 배포와 피드백 가능 | 검증이 PR 리뷰와 자동 테스트에 의존하므로 이 과정이 부실하면 문제가 `main`에 바로 반영될 수 있음 |

GitHub Flow는 테스트를 생략하는 전략이 아니라, **별도의 출시 브랜치 대신 PR 단계의 리뷰와 자동 테스트로 검증**하는 전략이다.

## 4. Git Flow vs GitHub Flow

### 4.1 비교표

| 비교 항목 | Git Flow | GitHub Flow |
|---|---|---|
| 핵심 브랜치 | `main`, `develop` + `feature`, `release`, `hotfix` | `main` + 작업 브랜치 |
| 계속 유지되는 브랜치 | `main`, `develop` (2개) | `main` (1개) |
| 작업 시작 브랜치 | `develop` (긴급 수정은 `main`) | `main` |
| 배포 방식 | 버전 단위로 계획된 출시 | 병합된 내용을 수시로 배포 |
| 출시 전 검증 | `release` 브랜치에서 테스트 | PR 리뷰와 자동 테스트 |
| 긴급 수정 | `hotfix` 브랜치 사용 | 작업 브랜치에서 수정 후 병합 |
| 복잡성 | 높음 | 낮음 |
| 협업 중심 | 브랜치별 역할 분담 | PR과 코드 리뷰 |

### 4.2 적합한 프로젝트 환경

| 전략 | 적합한 환경 |
|---|---|
| Git Flow | 대규모 팀, 정해진 일정에 버전을 출시하는 제품(앱 등), 여러 버전을 함께 관리해야 하는 프로젝트 |
| GitHub Flow | 소규모 팀, 자주 배포하는 웹 서비스, 빠른 개발과 피드백이 중요한 프로젝트 |

둘 중 하나가 무조건 더 좋은 것은 아니며, 실무에서는 팀의 규모와 배포 주기에 맞게 단순화하거나 변형해 사용하는 경우가 많다.

### 4.3 브랜치 이름의 차이

| 이름 | 설명 |
|---|---|
| `main` / `master` | 둘 다 저장소의 기본 브랜치를 뜻한다. 이전 자료는 `master`를 사용했고, GitHub는 2020년부터 새 저장소의 기본 브랜치 이름으로 `main`을 사용한다. |
| `develop` / `dev` | Git Flow의 공식 이름은 `develop`이다. `dev`는 프로젝트에서 정한 이름이며, 브랜치의 역할은 이름이 아니라 **팀이 정한 규칙**에 따라 결정된다. |

## 5. 우리 팀이 이번 과제에 적용한 방식

### 5.1 브랜치 구조

| 브랜치 | 역할 |
|---|---|
| `main` | 최종 결과물이 반영되는 브랜치. 직접 push하지 않음 |
| `dev` | 팀원들의 작업이 모이는 통합 브랜치 |
| `docs/이름` | `dev`에서 생성한 개인 작업 브랜치. 학습 정리 문서 작성용 |
| `docs/merge-summary` | 개인 문서를 이 최종본 하나로 취합하는 브랜치 |

```text
dev ──▶ docs/이름 ──(Commit·Push)──▶ PR ──(Review)──▶ dev
dev ──▶ docs/merge-summary ──(취합·개별 파일 삭제)──▶ PR ──▶ dev
dev ──(PR)──▶ main
```

### 5.2 우리 방식은 어느 쪽일까?

작업 브랜치를 짧게 쓰고 병합 후 삭제한다는 점은 GitHub Flow와 닮았다. 하지만 작업 브랜치의 생성·삭제는 Git Flow의 `feature` 브랜치도 똑같이 하는 일이라 두 전략을 가르는 기준이 되지 않는다.

두 전략을 가르는 진짜 기준은 **계속 유지되는 브랜치가 몇 개인가**이다. 우리 팀은 `main`과 `dev` 두 개를 계속 유지하므로 **Git Flow의 `develop`–`feature` 구조**에 해당한다. 다만 `release`, `hotfix`는 사용하지 않으므로 정확히는 **간소화한 Git Flow**이며, 병합은 GitHub Flow의 핵심인 PR과 코드 리뷰를 거친다.

| 구분 | 일반적인 Git Flow | 우리 팀 운영 방식 |
|---|---|---|
| 통합 브랜치 | `develop` | `dev` |
| 작업 브랜치 | `feature/*` | `docs/이름` 등 |
| 병합 방식 | PR과 리뷰를 거쳐 `develop`에 병합 | PR과 리뷰를 거쳐 `dev`에 병합 |
| `release`, `hotfix` | 사용 | 사용하지 않음 |

## 6. 주요 Git 명령어

| 명령어 | 핵심 역할 |
|---|---|
| `git clone 주소` | 원격 저장소를 처음 내려받기 |
| `git fetch origin` | 원격의 새 브랜치·커밋 정보 가져오기 (내 파일은 그대로) |
| `git switch 브랜치` | 브랜치 이동 |
| `git switch -c 브랜치` | 브랜치를 새로 만들면서 이동 |
| `git status` | 수정·스테이징된 파일과 현재 브랜치 상태 확인 |
| `git add` | 커밋할 변경 사항을 스테이징 영역에 추가 |
| `git rm` | 파일 삭제를 기록 |
| `git commit` | 스테이징된 변경 사항을 하나의 기록으로 저장 |
| `git push` | 로컬 커밋을 원격 저장소에 업로드 |
| `git pull` | 원격의 최신 변경 사항을 가져와 **현재 브랜치**에 병합 |

```bash
# dev를 최신 상태로 맞춘 뒤 개인 브랜치 생성 및 이동
git switch dev
git pull origin dev
git switch -c docs/git-flow-summary

# 변경 사항 확인 후 필요한 파일만 스테이징
git status
git add docs/git-flow-summary.md

# 변경 내용 기록 후 원격에 업로드 (-u: 원격 브랜치와 연결)
git commit -m "docs: Git Flow와 GitHub Flow 학습 내용 정리"
git push -u origin docs/git-flow-summary
```

`git add .`는 의도하지 않은 파일까지 추가될 수 있으므로 `git status`로 확인한 뒤 필요한 파일만 추가한다. 원격 기록을 덮어쓰는 `git push -f`는 공용 브랜치에서 사용하지 않는다.

## 7. 실습하며 배운 점

1. **`pull`은 브랜치를 옮겨주지 않는다.** `pull`은 현재 브랜치만 최신으로 맞춘다. 원격에 새로 생긴 `dev`를 받으려면 `git fetch` 후 `git switch dev`를 해야 한다.
2. **커밋하지 않은 새 파일(Untracked, `U`)은 어느 브랜치에도 속하지 않는다.** 그래서 브랜치를 옮겨도 작업 폴더에 그대로 따라온다. 원하는 브랜치에 있을 때 커밋해야 그 브랜치 소속이 된다.
3. **PR의 base는 자동으로 `main`이 잡힌다.** base를 확인하지 않고 머지했다가 작업이 `dev`가 아닌 `main`으로 바로 들어가는 실수를 겪었다. 이미 열린 PR은 제목 옆 연필 아이콘으로 base를 바꿀 수 있지만, 머지된 뒤에는 바꿀 수 없다.
4. **머지 전 "Files changed" 탭을 꼭 확인한다.** 아직 준비가 안 된 PR은 Draft로 바꿔 실수로 머지되는 것을 막고, 수정은 같은 브랜치에 커밋·푸시하면 PR에 자동 반영된다.
5. **브랜치 이름보다 팀의 규칙이 중요하다.** `dev`든 `develop`이든 팀이 정한 역할과 흐름을 모두가 지키는 것이 핵심이다.

### 학습 정리

- **Git Flow**는 여러 브랜치로 개발, 출시 준비, 긴급 수정을 분리해 안정적인 버전 관리를 중시한다.
- **GitHub Flow**는 `main`과 작업 브랜치, PR 리뷰만으로 단순하고 빠른 배포를 중시한다.
- 두 전략의 우열을 가리기보다 **프로젝트 규모와 배포 주기에 맞는 전략을 선택**하는 것이 중요하다.
- 공용 브랜치에서 직접 작업하지 않고 **작업 브랜치 → PR → 리뷰 → 병합** 순서를 지키면 충돌을 줄이고 변경 이력을 명확하게 남길 수 있다.
