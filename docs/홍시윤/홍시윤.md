# Git Branch 전략
먼저, Git Branch 전략은 여러 개발자가 하나의 저장소(Repository)를 함께 사용할 때, 코드의 충돌을 줄이고 효율적으로 협업하기 위해 브랜치 생성, 관리, 병합 규칙을 정해놓은 워크플로우(Workflow)이다. 
- 동시 작업 가능
- 코드 충돌(Merge Conflict) 최소화
- 안정적인 배포 및 롤백

<br><br><br>

## 1. Git Flow
Git Flow는 역할을 나누고, 여러 단계를 거쳐서 완성된 작품을 발표하는 방식이다.

ex) 팀 프로젝트로 그림책을 만든다고 가정
- 팀원 1: 그림 그리기
- 팀원 2: 이야기 쓰기
- 팀원 3: 오타 수정하기
- 팀원 4: 완성된 책 확인하기
 
===> 그림을 그리자마자 바로 완성된 책에 넣으면 문제가 생길 수 있음.<br>
===> 그렇기 때문에 단계별로 확인을 해야함.
<br><br>

#### branch 종류
- main: 정식으로 발표한 책 (사용자에게 공개된 안정적인 코드가 있는 곳)
- develop: 다음 책을 준비하는 곳 (여러 친구의 작업을 모아서 다음 버전을 만드는 곳)
- feature: 새 기능을 만드는 곳 (새 그림이나 이야기를 각자 따로 만드는 작업 공간)
- release: 발표 전 최종 점검 (오타나 오류를 확인하고 출시를 준비)
- hotfix: 긴급 수리 (이미 발표한 책에서 큰 문제가 발견되면 빠르게 고치는 작업)
<br><br>

#### 작업 순서
feature (새 기능 만들기)<br>
⬇️<br>
develop (작업들을 합치기)<br>
⬇️<br>
release (출시 전 확인하기)<br>
⬇️<br>
main (정식 출시)<br>



<br><br><br>


## 2. GitHub Flow
GitHub Flow는 Git Flow에 비해 훨씬 간단하다. 작업할 브랜치를 만들고, 작업이 끝나면 확인받고, 바로 합치는 방식이다.

ex) 팀 프로젝트로 그림책에 고양이 그림 추가한다고 가정
- main에서 새 작업 공간을 만듦 (이름은 add-cat)
- 그 공간에서 고양이를 그림
- 다 그렸으면 Pull Request(PR)를 만들어 팀원에게 보여줌
- 팀원이 확인 후 문제가 없을 시 main에 합침
- 수정된 그림책을 공개
<br><br>

===> GitHub Flow에서는 별도의 develop, release, hotfix 브랜치를 반드시 만들 필요가 없음.<br>
===> main을 항상 배포할 수 있는 상태로 유지하는 것이 기본 원칙임.

#### 작업 순서
main (현재 작품)<br>
⬇️<br>
작업 브랜치 (고양이 그림 그리기)<br>
⬇️<br>
Pull Request (팀원에게 검사받기)<br>
⬇️<br>
main에 합치기  (완료)<br>

<br><br><br>

## 3. Git Flow와 GitHub Flow의 차이 한눈에 보기
Git Flow = 여러 단계로 나눠 꼼꼼하게 출시하기 !<br>
GitHub Flow = 작업하고 확인받은 뒤 간단하게 합치기 !<br>

둘 중 하나가 무조건 더 좋은 것은 아니며, 프로젝트의 규모와 출시 방식에 따라 선택 !

<br><br>

| 구분 | Git Flow | GitHub Flow |
|---|---|---|
| 작업 단계 | 여러 단계로 나뉨 | 비교적 간단함 |
| 주요 브랜치 | `main`, `develop`, `feature`, `release`, `hotfix` | `main` + 작업 브랜치 |
| 출시 전 점검 | 별도의 `release` 브랜치 활용 가능 | PR 및 자동 테스트 등으로 확인 |
| 긴급 수정 | 보통 `hotfix` 브랜치 사용 | 작업 브랜치에서 수정 후 합침 |
| 잘 어울리는 상황 | 정기 출시, 여러 버전 관리 | 자주 배포하는 웹 서비스 |
| 배우기 쉬운 정도 | 상대적으로 복잡함 | 상대적으로 쉬움 |
