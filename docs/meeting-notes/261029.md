## 1. 6일차 AI 폐렴 예측 팀 회의 결정 사항
1. 모델: ResNet18 단독 (`E8_lung_crop`)
    - 검증 1,044장 기준 Recall 0.974, Accuracy 0.973으로 NFR-PRED-001 기준(Recall 0.90 이상, Accuracy 0.80 이상) 만족
    - 가볍고 Grad-CAM(히트맵) 코드가 이미 있어 3초 기준(NFR-PRED-002) 맞추기 쉬움
    - 앙상블(Recall 0.982)은 시간이 남으면 고려
2. `confidence`: AI가 내린 판정에 대한 확신 정도, 0~100 퍼센트, 소수점 둘째 자리까지
    - 폐렴 판정이면 폐렴일 확률, 정상 판정이면 정상일 확률 (판정 기준이 50%라서 항상 50 이상)
3. 엔드포인트: `/api/v1/medical-records/{record_id}/predictions`
    - POST: AI 폐렴 예측 (요청 본문 없음)
    - GET: 예측 결과 목록 조회
4. 권한: `StaffUser` (부서 제한 없음, pending만 403)
    - 근거: 권한 설명 "스태프(흉부 X-ray 관련 모든 읽기, 쓰기, 수정 작업 가능)", "대기자(마이페이지 외 모든 서비스 접근 불가)"
5. `heatmap_url`: nullable로 변경 (요구사항에서 선택사항, 히트맵 생성 실패해도 예측 결과는 저장)
6. 응답 코드: 새로 예측하면 201, 저장된 결과를 응답하면 200
7. `ai_model` 값: 모델 가중치 파일 이름과 동일하게 `E8_lung_crop`
8. 이미지 경로: 진료기록 등록 시 DB `image_url`에 실제 파일 경로(`private_uploads/xrays/...`)가 저장되므로 그대로 사용
    - 히트맵도 같은 방식으로 `private_uploads/heatmaps/`에 저장
9. 응답 스키마는 2개로 분리 (팀 규칙: 요구사항에 없는 필드는 응답에 넣지 않기)
    - 예측 응답: `is_pneumonia, confidence, heatmap_url`
    - 목록 응답: `id, is_pneumonia, confidence, heatmap_url, created_at, ai_model`


## 2. 6일차 AI 폐렴 예측 코드 작성하기 + 예측 API 설계하기 + 예측 API 작성하기
1. 설아: 뼈대 PR → dev 머지
    - `.gitignore`에 `private_uploads/`, `worker/models/*` 추가 (사진, 모델 가중치 커밋 방지)
    - `worker/model.py`: 가짜 `predict()` (항상 같은 결과 반환함, 실제 모델 넣기 전에도 팀원들이 작업할 수 있도록 먼저 작업해두기)
    - `main.py`: 예측 라우터 등록, 서버 시작 시(lifespan) `load_models()` 한 번 호출
    - 라우터·스키마 구역 주석, 명세서 틀(`6일차_폐렴예측_API_설계.md`)
2. **작업 전 필수 사항!!!!!!**
    - 팀원 모두 `git pull origin dev` 명령어로 최신화
    - 팀원 각자 브랜치 생성(`feat/prediction-api-이름`)
    - 브랜치 이름 잘 확인하고 작업 시작하기~!
3. `app/schema/`의 스키마 파일과 `app/apis/`의 라우터 파일 중 자신이 맡은 부분 작업
    - 시윤: AI 폐렴 예측 API (REQ-PRED-001) + 명세 1번
    - 지희: X-Ray·히트맵 파일 경로 함수 + 히트맵 nullable 마이그레이션 + 전체 흐름 테스트
    - 지수: 응답 스키마 2개 + 예측 결과 목록 API (REQ-PRED-002) + 명세 2번
    - 설아: AI 모델(`worker/model.py`), 뼈대, 명세 공통 사항·NFR, 작업 가이드
4. **지희(경로 함수·마이그레이션), 지수(스키마) 먼저 PR 열기** → 머지 (시윤 파트에 필요함)
5. 시윤(예측 API), 지수(목록 API) PR → 머지
6. 설아: 실제 모델 PR → 머지
7. 지희: 전체 흐름 테스트 (진료기록 등록 → 예측 201 → 재예측 200 → 목록 조회)
8. `dev`로 머지하는 PR 열기
    - 상세 작업 방법은 디스코드에 올린 작업 가이드 참고
9. `dev` → `main` PR 열기 (전원 리뷰)


## 4. 과제 진행하며 느낀 점
- 점점 다들 작업 속도가 향상되고 있다 👍
- AI를 활용하더라도 코드를 본인이 이해하고 있어야 한다는 과제 요구사항이 왜 생겼는지 잘 알 것 같다. AI가 쭉 작성을 해줘도 내가 그걸 이해하고 있지 않으면 코드 리뷰를 할 수도, 리뷰를 받아도 이해가 힘들다...
- PR 리뷰가 끝나고 머지가 완료되고 해당 브랜치에서 더이상 작업할 것이 없다면 브랜치를 정리하는 습관이 필요할 것 같다.
    1. GitHub에서 브랜치 삭제하는 방법
        1) `dev` 옆 `[현재 브랜치 개수] Branches` 클릭
        2) 머지된(보라색 아이콘) 본인 브랜치만 삭제하기 (휴지통 아이콘 클릭)
        3) **잘못 지웠으면 새로고침하기 전까지 되돌리기 가능!!!!!!!!!!!**
            - PR이 있었던 브랜치라면 PR 페이지 아래쪽에 `Restore branch`로 되살리기도 가능
    2. 로컬 브랜치 정리하기
        1) 지울 브랜치에 들어가서 `git status`로 아직 커밋 안된 파일이 있나 확인
        2) 없으면 `dev`로 이동
        3) `git pull origin dev`
        4) `git branch -d 브랜치이름`
        5) 삭제되면 완료~
        6) 삭제가 안된다면 AI한테 에러 메세지 복붙하고 이유 물어보기 ㅎㅎ
    3. 로컬 브랜치와 GitHub 원격브랜치 전부 삭제했다면 `git fetch --prune`로 로컬-원격 동기화하기
