## 1. User API 설계하기
1. 팀장: `docs/user-api-template` 브랜치 생성
2. 한 파일에 작업하기 위해 뼈대(template) 파일(`4일차_USER_API_설계.md`) 작성
3. `dev` 브랜치로 Merge(PR 통해)
4. 팀원 모두 `git pull origin dev` 명령어로 최신화
5. 요구사항 정의서 중 자신이 맡을 부분 선택
    - 시윤: 회원가입, 로그인, 토큰 재발급 (인증 담당)
    - 지수: 회원 탈퇴, 마이페이지 조회 (마이페이지 담당)
    - 지희: 회원 정보 수정, 비밀번호 변경, 로그아웃 (마이페이지 수정 담당)
    - 설아: 회원 목록 조회, 회원 권한 변경 (어드민 담당)
6. 각자 브랜치 생성 `feat/user-api-이름` (이후 API 작성까지 이어서 할 예정)
7. 뼈대 파일에 각자 맡은 부분만 내용 추가 진행
8. `dev` 브랜치로 Merge(PR 통해)
    - 머지 후 브랜치 삭제하지 않기(같은 브랜치에서 API 코드 작업 이어서 함)


## 2. User API 작성하기
1. 팀장: `feat/user-api-template` 브랜치 생성
2. 설계한 API에 따라 공통 부분 정의 파일 생성
    - 값 정의(권한, 부서, 성별): `app/models/enums.py`(기존 파일 사용, 값을 명세서 기준 소문자, develop으로 수정)
    - 토큰/비밀번호 관련 함수: `app/core/security.py`
        - `hash_password`, `verify_password`: 비밀번호 해시/확인 (pwdlib, Argon2)
        - `create_access_token`, `create_refresh_token`: 토큰 만들기 (액세스는 `SECRET_KEY` 30분, 리프레시는 `REFRESH_SECRET_KEY` 7일)
        - `decode_access_token`, `decode_refresh_token`: 토큰 해석해서 user_id 반환
        - 토큰 안 키 이름은 `user_id`
        - `set_refresh_cookie`, `delete_refresh_cookie`: 리프레시 토큰 쿠키 심기/지우기(이름 `refresh_token`, Path `/api/v1/auth`) -> 로그인/로그아웃은 쿠키를 직접 다루지 말고 이 함수 사용하기
    - 인증 함수(로그인 유저 가져오기, 어드민 확인): `app/apis/dependencies.py` (비동기 방식)
        - `get_current_user`: 로그인한 유저 반환(토큰 없음/만료/없는 유저면 401 에러, 비활성 유저면 403 에러)
        - `get_current_admin`: admin만 통과, 아니면 403 에러
        - `get_current_staff`: staff, admin만 통과, 아니면 403 에러
        - 사용법: 
            1) API .py 파일에 `from app.apis.dependencies import AdminUser, DBSession`처럼 필요한 타입 별칭 import
            2) `user: AdminUser`, `db: DBSession` 처럼 사용(CurrentUser, StaffUser도 동일)
3. 라우터 파일 3개 빈 상태로 만들기(각자 작업할 파일 미리 생성)
4. `main.py`에 라우터 등록
5. `dev` 브랜치로 Merge(PR 통해)
6. **작업 전 필수 사항!!!!!!**
    - 팀원 모두 `git pull origin dev` 명령어로 최신화
    - 팀원 모두 `uv sync`로 동일 환경 세팅
    - **JWT 설정** 
        - 각자 `.env` 파일 생성 (`.env.example` 참고)
        - 터미널에 `uv run python -c "import secrets; print(secrets.token_hex(32))"` 실행
        - 나온 값을 `SECRET_KEY`에 할당
        - 명령어 한 번 더 실행 (방향키 위로 누르면 동일한 명령어 입력됨)
        - 나온 값을 `REFRESH_SECRET_KEY`에 할당
7. 라우터 파일 중 자신이 맡은 부분 작업
    - 인증 담당(시윤): `auth` 라우터 (회원가입, 로그인, 토큰 재발급)
    - 마이페이지 담당(지희, 지수): `users` 라우터 (/users/me 관련 전부)
    - 어드민 담당(설아): `admin` 라우터 (회원 목록 조회, 회원 권한 변경)
8. `dev` 브랜치로 Merge(PR 통해)


## 3. 과제 진행하며 느낀 점
- 3일차 과제 진행하면서 PR을 열고 서로 의견을 주고 받는 걸 드디어 해보았다.
    - Approve(승인): 문제없음
    - Comment(의견만): 질문이나 가벼운 제안, Merge를 막지 않음
        1) 작성자가 답변만 하면 되는 경우 -> 리뷰어가 확인 후 Merge
        2) 답변하다 수정이 필요해진 경우 -> 아래 Request Changes 흐름과 동일
    - Request changes(수정 요청): 고쳐야 Merge 가능(Merging is blocked)
        1) 작성자가 같은 브랜치에서 수정 커밋 푸시 -> PR에 자동 반영
        2) 각 코멘트에 "수정했습니다" 등 답글 후 Resolve conversation
        3) 리뷰어 옆 🔁 버튼으로 재요청
        4) 리뷰어가 "View reviewed changes"로 바뀐 부분만 확인
            - 다 고쳐짐 -> Approve
            - 아직 부족 -> 다시 Request changes
        5) 작성자가 리뷰 내용에 동의하지 않는 경우 -> 코멘트로 이유를 설명하고 합의 (결론이 나지 않는 경우 팀 오픈채팅방이나 팀 코어시간에 팀 회의)
