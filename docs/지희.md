# Git Flow와 GitHub Flow 브랜치 전략 학습 정리

- **작성자:** 지희
- **파일:** `docs/지희.md`
- **목적:** 팀 프로젝트의 Git/GitHub 협업 방식을 이해하기 위해 대표적인 브랜치 전략인 Git Flow와 GitHub Flow를 정리한다.

---

## 1. Git 브랜치 전략이란?

### 1.1 브랜치(Branch)

브랜치는 **기존 코드에 영향을 주지 않고 독립적으로 작업하기 위한 작업 공간**이다. 원본 문서를 복사해 만든 작업용 사본과 비슷하다. 작업이 끝나면 변경 내용을 원래 브랜치에 병합(Merge)한다.

### 1.2 브랜치 전략

브랜치 전략은 여러 개발자가 하나의 저장소에서 협업할 때 **브랜치를 어디서 만들고, 어떤 이름을 붙이고, 언제 어디로 병합할지** 정해 둔 팀의 공통 규칙이다.

| 필요한 이유 | 설명 |
|---|---|
| 동시 작업 | 기능별 브랜치에서 작업하므로 서로의 작업에 영향을 주지 않는다. |
| 작업 추적 | 브랜치가 기능·이슈 단위로 나뉘어 있어 변경 이력을 파악하기 쉽다. |
| 안정성 | 배포용 브랜치에는 검토를 거친 코드만 반영된다. |
| 코드 리뷰 | 병합 전에 Pull Request로 팀원의 검토를 받을 수 있다. |

## 2. Git Flow

### 2.1 정의와 특징

Git Flow는 2010년 Vincent Driessen이 제안한 브랜치 모델이다. 역할이 정해진 여러 브랜치를 사용해 **개발, 출시 준비, 긴급 수정을 분리**하고, 버전 단위의 체계적인 릴리스 관리를 목표로 한다.

### 2.2 브랜치별 역할

| 브랜치 | 생성 위치 | 병합 대상 | 역할 |
|---|---|---|---|
| `main` | - | - | 배포 가능한 최종 제품 상태를 보관 |
| `develop` | `main` | `release`를 거쳐 `main` | 개발 중인 기능을 통합 |
| `feature/*` | `develop` | `develop` | 새로운 기능 개발 |
| `release/*` | `develop` | `main`, `develop` | 출시 전 테스트와 버그 수정 |
| `hotfix/*` | `main` | `main`, `develop` | 배포 후 발견된 긴급 버그 수정 |

`main`과 `develop`은 계속 유지되는 브랜치이고, 나머지는 필요할 때 만들었다가 병합 후 삭제한다.

### 2.3 개발 및 배포 흐름

```text
develop ──▶ feature/기능 ──(PR·리뷰)──▶ develop
develop ──▶ release/버전 ──(테스트·수정)──▶ main(배포, 버전 태그) + develop
main    ──▶ hotfix/버전  ──(긴급 수정)──▶ main + develop
```

1. `develop`에서 `feature` 브랜치를 만들어 기능을 개발한다.
2. 완료된 기능은 Pull Request와 리뷰를 거쳐 `develop`에 병합한다.
3. 출시할 기능이 모이면 `develop`에서 `release` 브랜치를 만들어 테스트하고 버그를 수정한다.
4. 테스트가 끝나면 `release`를 `main`에 병합해 배포하고, 같은 내용을 `develop`에도 병합한다.
5. 배포 후 긴급 버그가 생기면 `main`에서 `hotfix`를 만들어 수정하고 `main`과 `develop`에 모두 반영한다.

### 2.4 장단점

| 장점 | 단점 |
|---|---|
| 브랜치 역할이 명확해 대규모 협업에 적합 | 브랜치 종류가 많아 구조가 복잡 |
| `release`, `hotfix`를 통한 명확한 배포 절차 | 병합 경로가 많아 관리 부담이 큼 |
| 버전 관리와 롤백이 체계적 | 수시로 빠르게 배포해야 하는 환경에는 무거움 |

## 3. GitHub Flow

### 3.1 정의와 특징

GitHub Flow는 GitHub에서 제안한 **단순한 브랜치 기반 작업 흐름**이다. 항상 배포 가능한 `main` 브랜치 하나와 짧게 사용하는 작업 브랜치로 운영하며, **Pull Request와 코드 리뷰**를 중심으로 협업한다. 자주 배포하는 웹 서비스처럼 빠른 개발과 피드백이 중요한 환경에 적합하다.

### 3.2 main과 작업 브랜치

| 브랜치 | 역할 |
|---|---|
| `main` | 항상 배포 가능한 상태를 유지한다. 직접 작업하지 않고 PR을 통해서만 변경한다. |
| 작업 브랜치 | `main`에서 생성하며 하나의 기능이나 수정 작업을 담당한다. 병합 후 삭제한다. |

### 3.3 작업 흐름

```text
Branch → Commit → Push → Pull Request → Review → Merge
```

| 단계 | 내용 |
|---|---|
| Branch | 최신 `main`에서 작업 내용이 드러나는 이름으로 브랜치 생성 |
| Commit | 의미 있는 단위로 변경 사항 기록 |
| Push | 작업 브랜치를 원격 저장소(GitHub)에 업로드 |
| Pull Request | `main`에 병합해 달라는 요청을 생성하고 변경 내용 설명 |
| Review | 팀원이 검토하고, 수정 요청이 있으면 같은 브랜치에 커밋·푸시하여 반영 |
| Merge | 승인 후 `main`에 병합하고 작업 브랜치 삭제 |

### 3.4 Pull Request의 base와 compare

```text
base: main  ←  compare: feature/login
(병합될 대상 브랜치)   (변경 내용을 가진 브랜치)
```

PR은 **compare 브랜치의 변경 내용을 base 브랜치로 병합**하는 요청이다.

### 3.5 장단점

| 장점 | 단점 |
|---|---|
| 구조가 단순해 배우고 적용하기 쉬움 | 별도의 릴리스 브랜치가 없어 버전 단위 관리가 어려움 |
| PR 중심이라 코드 리뷰가 자연스럽게 이루어짐 | 여러 버전을 동시에 유지보수하기 어려움 |
| 작게 자주 병합하므로 빠른 배포와 피드백 가능 | 검증이 PR 리뷰와 자동 테스트에 의존하므로 이 과정이 부실하면 문제가 `main`에 바로 반영될 수 있음 |

GitHub Flow는 테스트를 생략하는 전략이 아니라, **별도의 출시 브랜치 대신 PR 단계의 리뷰와 자동 테스트로 검증**하는 전략이다.

## 4. Git Flow vs GitHub Flow

### 4.1 비교표

| 비교 항목 | Git Flow | GitHub Flow |
|---|---|---|
| 핵심 브랜치 | `main`, `develop` + `feature`, `release`, `hotfix` | `main` + 작업 브랜치 |
| 작업 시작 브랜치 | `develop` (긴급 수정은 `main`) | `main` |
| 배포 방식 | 버전 단위로 계획된 출시 | 병합된 내용을 수시로 배포 |
| 검증 방식 | `release` 브랜치에서 출시 전 테스트 | PR 리뷰와 자동 테스트 |
| 복잡성 | 높음 | 낮음 |
| 협업 중심 | 브랜치별 역할 분담 | PR과 코드 리뷰 |

### 4.2 적합한 프로젝트 환경

| 전략 | 적합한 환경 |
|---|---|
| Git Flow | 대규모 팀, 정해진 일정에 버전을 출시하는 제품, 여러 버전을 함께 관리해야 하는 프로젝트 |
| GitHub Flow | 소규모 팀, 자주 배포하는 웹 서비스, 빠른 개발과 피드백이 중요한 프로젝트 |

실무에서는 두 전략을 그대로 쓰기보다 팀의 배포 환경과 규모에 맞게 단순화하거나 변형해 사용하는 경우가 많다.

### 4.3 브랜치 이름의 차이

| 이름 | 설명 |
|---|---|
| `main` / `master` | 둘 다 저장소의 기본 브랜치를 뜻한다. Git Flow 원문 등 이전 자료는 `master`를 사용했고, GitHub는 2020년부터 새 저장소의 기본 브랜치 이름으로 `main`을 사용한다. |
| `develop` / `dev` | Git Flow의 공식 이름은 `develop`이다. `dev`는 프로젝트에서 정한 이름이며, 브랜치의 역할은 이름이 아니라 **팀이 정한 규칙**에 따라 결정된다. |

## 5. 우리 팀 프로젝트에 적용한 브랜치 전략

### 5.1 브랜치별 역할

| 브랜치 | 우리 팀에서의 역할 |
|---|---|
| `main` | 기본 브랜치. 최종 결과물이 반영되는 브랜치 |
| `dev` | 팀원들의 작업이 모이는 통합 브랜치 |
| `docs/jihee` | `dev`에서 생성한 개인 작업 브랜치. 학습 정리 문서 작성용 |

### 5.2 진행 현황과 예정된 작업 흐름

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | `dev`에서 개인 브랜치 `docs/jihee` 생성 | 완료 |
| 2 | `docs/지희.md` 파일 생성 | 완료 |
| 3 | Markdown 학습 내용 작성 및 수정 | 진행 중 |
| 4 | 개인 브랜치에 Commit 및 Push | 예정 |
| 5 | `dev`를 base로 Pull Request 생성 | 예정 |
| 6 | 팀 규칙에 따라 리뷰어 지정, 리뷰 후 병합 | 예정 |

```text
dev ──▶ docs/jihee ──(Commit·Push)──▶ Pull Request ──(Review)──▶ dev
```

예정된 PR은 **base: `dev` ← compare: `docs/jihee`** 방향으로 생성한다.

### 5.3 일반적인 Git Flow와의 비교

| 구분 | 일반적인 Git Flow | 우리 팀 운영 방식 |
|---|---|---|
| 통합 브랜치 | `develop` | `dev` |
| 작업 브랜치 | `feature/*` | `docs/jihee` 등 작업 종류를 나타내는 개인 브랜치 |
| 병합 방식 | PR과 리뷰를 거쳐 `develop`에 병합 | PR과 리뷰를 거쳐 `dev`에 병합 |
| `release`, `hotfix` | 사용 | 현재 실습 규칙에 포함되어 있지 않음 |

우리 팀은 `main`과 별도의 통합 브랜치 `dev`를 두고 그 위에서 개인 브랜치를 만들어 작업한다. 이는 **Git Flow의 `develop`–`feature` 구조**와 같은 방식이다. 병합은 GitHub Flow의 핵심인 **PR과 코드 리뷰**를 거친다.

## 6. 주요 Git 명령어 및 학습 정리

### 6.1 주요 명령어

| 명령어 | 핵심 역할 |
|---|---|
| `git switch` | 브랜치 이동, `-c` 옵션으로 생성 후 이동 |
| `git status` | 수정·스테이징된 파일과 현재 브랜치 상태 확인 |
| `git add` | 커밋할 변경 사항을 스테이징 영역에 추가 |
| `git commit` | 스테이징된 변경 사항을 하나의 기록으로 저장 |
| `git push` | 로컬 커밋을 원격 저장소에 업로드 |
| `git pull` | 원격 저장소의 최신 변경 사항을 가져와 현재 브랜치에 병합 |

### 6.2 사용 예시

```bash
# dev를 최신 상태로 맞춘 뒤 개인 브랜치 생성 및 이동
git switch dev
git pull origin dev
git switch -c docs/jihee dev

# 변경 사항 확인 후 커밋할 파일만 스테이징
git status
git add docs/지희.md

# 변경 내용 기록
git commit -m "docs: Git Flow와 GitHub Flow 학습 내용 정리"

# 원격 저장소에 개인 브랜치 업로드 (-u: 원격 브랜치와 연결)
git push -u origin docs/jihee
```

`git add .`는 의도하지 않은 파일까지 추가될 수 있으므로 `git status`로 확인한 뒤 필요한 파일만 추가한다. 원격 기록을 덮어쓰는 `git push -f`는 공용 브랜치에서 사용하지 않는다.

### 6.3 학습 정리

- **Git Flow**는 여러 브랜치로 개발, 출시 준비, 긴급 수정을 분리해 안정적인 버전 관리를 중시한다.
- **GitHub Flow**는 `main`과 작업 브랜치, PR 리뷰만으로 단순하고 빠른 배포를 중시한다.
- 두 전략의 우열을 가리기보다 **프로젝트 규모와 배포 주기에 맞는 전략을 선택**하는 것이 중요하다.
- 공용 브랜치에서 직접 작업하지 않고 **개인 브랜치 → PR → 리뷰 → 병합** 순서를 지키면 팀원 간 작업 충돌을 줄이고 변경 이력을 명확하게 남길 수 있다.
- PR은 **compare 브랜치를 base 브랜치로 병합**하는 요청이므로, 생성 시 base가 팀 규칙에 맞는 브랜치(`dev`)인지 확인해야 한다.
- 브랜치 이름(`main`/`master`, `dev`/`develop`)보다 **팀이 정한 브랜치의 역할과 규칙**을 이해하는 것이 중요하다.
