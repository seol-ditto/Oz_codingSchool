## 1. 각 디렉터리의 역할과 작성해야 할 파일의 내용

| 디렉토리 | 역할 | 작성 파일 |
| --- | --- | --- |
| `app/core/` | 프로젝트 전체가 공통으로 사용하는 핵심 설정 및 기능 관리 | 환경설정 `config.py`<br>DB 연결 `db/databases.py`<br>모델 공통 Base`db/models.py` |
| `app/models/` | SQLAlchemy ORM으로 DB 테이블을 정의<br>클래스 하나가 테이블 하나이며, 데이터의 생성/조회/수정/삭제 작업 활용 가능 | `user.py`, `patient.py`, `medical_record.py`, `xray_image.py`, `ai_analysis_result.py`, `__init__.py` |
| `app/repositories/` | DB와 상호작용하여 데이터를 조회/생성/수정/삭제하는 작업 담당(데이터베이스에 접근하는 코드는 별도로 관리) | `patient_repository.py`, `medical_record_respository.py` 등 DB에 직접 접근하는 코드 파일 |
| `app/schemas/` | API 요청 및 응답에 사용되는 데이터의 구조와 형식을 정의하고 데이터 유효성을 검증(pydantic 모델 활용) | `user.py`에 회원가입 요청(`UserCreate`), 응답(UserResponse) 등 |
| `app/services/` | 업무 규칙(비즈니스 로직)을 처리<br>DB에 직접 접근하지 않고 respository/를 통해 작업 수행 | `user_service.py`에서 이메일 중복 확인, 비밀번호 해싱<br>`xray_service.py`에서 이미지를 `media/`에 저장한 뒤 경로를 DB에 기록 |
| `app/apis/` | 엔드포인트(URL)을 정의하는 라우터를 정의<br>외부의 요청을 받아 프로그램 내부의 기능과 연결해주는 역할 담당 | `user_api.py`에 API를 구성하고 `main.py`에 라우터 등록 |
## 2. 각 파일의 역할
| 파일명 | 역할 |
| --- | --- |
| `app/main.py` | FastAPI 애플리케이션을 생성하고 실행에 필요한 구성 요소를 연결하는 파일<br> - FastAPI 애플리케이션 인스턴스 생성(`app = FastAPI()`)<br> - API 라우터 등록 및 연결<br> - 프로그램이 요청 받을 수 있도록 필요한 설정 수행(로그인 요청을 사용자가 보내면 `main.py`에 등록된 API 경로를 통해 요청이 처리될 수 있도록 함 |
| `app/core/config.py` | 애플리케이션 전반에서 사용하는 설정값을 관리하는 파일<br>환경변수를 활용해 개발/운영 환경에 필요한 설정 관리 |
| `pyproject.toml` | 프로젝트의 기본 정보와 실행 환경 및 의존성 등을 정의하는 설정 파일 <br> - 프로젝트 이름, Python 버전, fastapi 등 필요한 라이브러리와 버전 조건, 개발 도구 및 빌드 관련 설정 관리<br> - 이 파일을 통해 같은 프로젝트를 팀원이 같은 환경에서 실행하고 관리할 수 있음 |
| `uv.lock`  | 실제 설치되는 라이브러리의 정확한 버전과 하위 의존성까지 고정한 파일<br> - 팀원이 `uv sync`를 하면 모두 같은 버전으로 설치되어 "내 컴퓨터에서는 되는데?" 문제를 방지할 수 있음 <br> - 자동 생성 파일, 직접 수정 X|

## 4. SQLAlchemy를 활용하여 모델을 작성하고 alembic을 활용하여 마이그레이션을 수행하는 방법
1. `app/core/db/models.py`의 Base를 상속해서 `app/models/`에 ERD 테이블 5개를 클래스로 작성
    - 컬럼 타입, NOT NULL, FK를 ERD대로 지정
2. `app/models/__init__.py`에서 5개 모델을 모두 import(빠트린 모델은 alembic이 테이블 인식하지 X)
3. `alembic/env.py`에서 DB 주소를 `settings`에서 읽고, `target_metadata = Base.metadata`로 모델 연결, SQLite용으로 `render_as_batch=True` 설정
4. `alembic revision --autogenerate -m "create tables"` 실행 -> `alembic/versions/`에 마이그레이션 파일 생성됨. (테이블 5개 전부 들어있는지 확인!)
5. `alembic upgrade head`로 DB에 반영하면 `app.db`에 테이블 5개와 버전 기록용 `alembic_version` 테이블이 생성됨
6. DB Browser for SQLite로 열어 스키마 확인
    - 모델 수정 시 4~5번 반복
    - 잘못 됐으면 `alembic downgrade -1`로 되돌리기


## 5. API 구현 흐름
1. **API (`apis/`)**: 클라이언트의 HTTP 요청을 받고 적절한 서비스를 호출
2. **Schema (`schemas/`)**: 요청 데이터의 형식과 유효성을 검증하고 응답 데이터의 구조를 정의
3. **Service (`services/`)**: 애플리케이션의 비즈니스 로직을 처리
4. **Repository (`repositories/`)**: 데이터베이스의 데이터를 조회하거나 저장·수정·삭제
5. **Model (`models/`)**: 데이터베이스 테이블과 컬럼의 구조를 정의
6. **API 응답 반환**: 처리 결과를 클라이언트에 반환

**전체 흐름**

> 클라이언트 요청 → API → Schema 검증 → Service → Repository → Database → 응답 반환

### API 구현 흐름 예시(엑스레이 업로드)
1. 클라이언트가 `POST /xray-images`로 이미지와 진료기록 id 보냄
2. `apis/`의 라우터가 요청을 받고, `schemas/`의 요청 형식으로 데이터 검증
3. 라우터가 `services/`의 업로드 함수를 호출
4. service가 해당 진료기록이 있는지 `repositories/`로 조회 -> 이미지를 `media/`에 저장
5. service가 `models/`의 `XrayImage` 객체를 만들고 repository를 통해 DB에 저장
6. 저장 결과를 `schemas/`의 응답 형식으로 바꿔 클라이언트에게 돌려줌
