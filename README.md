## 3. API 명세서 작성
- 4일차 USER API 명세서를 작성하면서 '개요 → 요청 → 성공·실패 응답 → 비고'로 구성된 공통 양식을 정하고, 이를 5일차 환자·진료기록 API와 6일차 AI 예측 API에도 적용했다.
- API별 엔드포인트, HTTP 메서드, 인증 여부, 요청·응답 필드와 오류 상황을 정의하고, 팀원 간 분담 및 리뷰를 통해 명세를 보완했다.
- 필드명은 `snake_case`, Enum 값은 소문자, 오류 응답은 `{"detail": "..."}` 형식으로 통일하고, 인증이 필요한 API에는 Bearer 토큰 헤더를 사용하도록 정했다.
- 요구사항에 명시되지 않은 필드나 동작은 팀 회의로 결정하고, 그 근거를 명세서 비고란에 기록했다.
- 7일차 화면 연결 과정에서는 `patient_id`, `role`, `id` 필드 3개와 이미지 파일 API 2개를 추가하여 실제 화면 구현에 필요한 사항을 반영했다.

## 4. Git & GitHub 브랜치 전략
- Git Flow와 GitHub Flow를 함께 공부한 뒤, `main`과 `dev`를 유지하는 간소화한 Git Flow를 우리 팀의 브랜치 전략으로 채택했다.
    - `main`: 최종 결과물, `dev`: 팀원 작업이 모이는 통합 브랜치
    - 위 브랜치 두 가지는 직접 push를 금지하고, PR을 통해서만 머지했다.
    - 작업 브랜치는 항상 최신 `dev`에서 `feat/`, `fix/`, `docs/`, `refactor/` + 하는 일 + 이름으로 만들고, 머지가 완료되면 삭제했다.
- 커밋 메시지는 팀 규칙에 따르기로 했다.
- 리뷰어 마니또로 리뷰어를 정해 최소 1명 승인 후 머지를 진행했다(본인 PR은 본인이 머지하지 않음).
    - `dev` → `main` PR은 팀원 전원 확인 후 머지를 진행했다.
- 여러 명이 한 파일을 고칠 때는 주석으로 담당 구역을 분리하고, 개인 작업을 모은 뒤 취합용 브랜치에서 양식을 통일해 `dev`로 최종 머지를 진행했다(conflict를 줄이기 위해서).
- 디스코드 채널에 GitHub 웹훅을 연결해 PR 생성 및 리뷰 알림을 받을 수 있도록 했다.

- 자세한 내용: [브랜치 전략](docs/2일차_git_branch_전략.md), [Git & GitHub 규칙](docs/1일차_team_rules.md#git--github-rules)

## 5. 프로젝트 세팅
- `uv sync`로 의존성을 설치하고, MySQL과 `.env`에 DB 연결 정보 및 서로 다른 `SECRET_KEY`, `REFRESH_SECRET_KEY`를 설정했다.
- AI 모델 가중치는 드라이브에서 내려받아 `worker/models/E8_lung_crop.pth`에 배치했다. 가중치 파일은 GitHub에 포함하지 않았다.
- Alembic 마이그레이션을 적용한 뒤 `uv run fastapi run app/main.py`로 서버를 실행했다. 최초 실행 시 폐 위치 모델(PSPNet) 다운로드로 시작 시간이 추가로 소요될 수 있다.
- 테스트 계정은 회원가입으로 생성하되, 첫 관리자 계정은 화면에서 권한을 변경할 수 없어 DBeaver에서 `role`을 대문자 `ADMIN`으로 직접 수정했다.
- 이후 관리자 계정으로 로그인해 다른 회원의 권한을 설정하고 API 및 화면 동작을 확인했다.

- DB 마이그레이션: [3일차 DB 마이그레이션](docs/3일차_db_migration.md)
- 테스트 계정: [테스트 계정 가이드](docs/7일차_테스트계정_가이드.md)

### Alembic Migration Guide

이 프로젝트는 데이터베이스 마이그레이션을 위해 Alembic을 사용한다.

#### 1. 마이그레이션 파일 생성 (자동 생성)
모델(`app/models/`)이 변경된 경우 다음 명령어를 실행하여 마이그레이션 파일을 생성한다.
```bash
uv run alembic revision --autogenerate -m "변경 내용 설명"
```

#### 2. 데이터베이스에 반영
생성된 마이그레이션을 데이터베이스에 적용하려면 다음 명령어를 실행한다.
```bash
uv run alembic upgrade head
```

#### 3. 이전 상태로 되돌리기 (Rollback)
마지막 마이그레이션을 취소하려면 다음 명령어를 실행한다.
```bash
uv run alembic downgrade -1
```

## 6. API 및 AI 워커 코드 작성과 병합
- 프로젝트 구조: [3일차 프로젝트 뜯어보기](docs/3일차_프로젝트_뜯어보기.md)
    - 3일차 문서는 API → Schema → Service → Repository 흐름을 소개하지만, 실제 구현에서는 `services/`·`repositories/` 없이 라우터(`app/apis/`)에서 스키마로 요청을 검증한 뒤 SQLAlchemy로 DB를 바로 조회·저장했다.

### 일차별 분담
요구사항 정의서를 기능(API) 단위로 나눠서, 한 사람이 같은 일차의 **명세서 → 스키마 → 라우터**를 이어서 작성했다. 서로 이어지는 기능(회원가입·로그인·토큰 재발급)은 한 사람이 묶어서 맡아 토큰·쿠키 규칙이 어긋나지 않게 했다.

| 일차 | 홍시윤 | 이지희 | 김지수 | 김설아 |
| --- | --- | --- | --- | --- |
| 4일차 USER API | 회원가입, 로그인, 토큰 재발급 | 회원 정보 수정, 비밀번호 변경, 로그아웃 | 마이페이지 조회, 회원 탈퇴 | 회원 목록 조회, 회원 권한 변경 |
| 5일차 환자·진료기록 API | 환자 정보 등록, 환자 목록 조회 | 환자 정보 상세 조회, 환자 정보 수정 | 환자 정보 삭제, 진료기록 등록 | 진료기록 목록 조회, 진료기록 상세 조회 |
| 6일차 AI 예측 API | AI 폐렴 예측 | X-Ray·히트맵 파일 경로 함수, DB 마이그레이션 | 예측 결과 목록 조회, 응답 스키마 | AI 모델 함수(`worker/`) |

- 코드 위치: 4일차 `app/apis/auth.py`·`users.py`·`admin.py`, 5일차 `patients.py`·`medical_records.py`, 6일차 `predictions.py` (요청·응답 스키마는 `app/schemas/`)

### 공통 코드를 먼저 만들고, 각자 구역에 작성
- **공통 코드:** `app/core/security.py`(비밀번호 해시, JWT 발급·해석, 리프레시 토큰 쿠키 설정·삭제)와 `app/apis/dependencies.py`(`DBSession`, 로그인 확인 `CurrentUser`, 권한별 `StaffUser`·`AdminUser`·`MedicalStaffUser`)를 먼저 만들어 두었다. 각 API는 이 별칭을 함수 인자에 쓰는 것만으로 로그인·권한 확인이 되어, 모든 API의 401(인증 실패) → 403(비활성 회원) → 403(대기자) → 403(의료진 아님) 순서와 에러 메시지가 같다.
- **구역 주석:** 같은 파일을 여러 명이 써야 해서 `# ===== [이름] 기능 =====` 헤더를 먼저 만들어 두고, 자기 구역 아래에만 작성했다. 다른 사람 구역과 구역 사이 빈 줄은 건드리지 않아 충돌을 줄였다.
- **스키마 작성 규칙:** [스키마 작성 가이드](docs/schemas_작성_가이드.md)에 따라 이름은 `기능 + Request/Response`로 짓고, 필드와 필수 여부는 명세서 표와 똑같이 맞췄다. 요구사항에 없는 필드는 추가하지 않는 것이 원칙이고, 화면 연결에 꼭 필요하면 회의로 정해 명세서 비고에 이유를 적었다. 권한·부서·성별은 enum을 쓰고, DB 객체를 그대로 응답하는 스키마에는 모든 스키마 파일에 `from_attributes=True`를 넣기로 통일했다.
- **명세서 = 코드:** 엔드포인트, 상태 코드, 에러 메시지(`{"detail": "메시지"}`), 응답 필드를 명세서와 똑같이 작성했다. 422는 FastAPI가 자동으로 만드는 모양을 그대로 따른다.

### 브랜치 전략대로 병합
우리 팀은 `main`(최종 결과물, 직접 push 금지)과 `dev`(통합) 두 브랜치를 유지하고, release·hotfix 없이 PR 리뷰를 거치는 **간소화한 Git Flow**로 운영했다. 자세한 내용은 [4. Git & GitHub 브랜치 전략](#4-git--github-브랜치-전략)을 참고한다.

1. `dev`에서 작업 브랜치(`feat/기능-이름` 등)를 만들어 내 구역을 작성하고, PR 전에 `/docs`에서 직접 테스트한다.
2. `feat` → `dev`로 PR을 올린다. PR의 base는 기본값이 `main`으로 잡히기 때문에 **`dev`로 바뀌었는지 확인**한 뒤 올렸다.
3. 리뷰어(마니또)가 [스키마 작성 가이드](docs/schemas_작성_가이드.md)의 리뷰 체크리스트(내 구역만 작성했는지, 필드가 명세서와 같은지, `from_attributes=True`가 있는지, 새 import를 PR 본문에 적었는지 등)로 확인한다.
4. 공용 파일의 맨 위 import 줄에서 충돌이 자주 났다. 최신 `dev`를 내 브랜치에 반영해서 충돌을 풀고(`Accept Both Changes` 후 중복된 import만 정리) 다시 푸시했다.
5. 최종 결과물은 `dev` → `main` PR로 병합한다.

**서로의 PR 리뷰에서 고친 것**
- 진료기록 등록의 차트 번호 중복(409) 응답이 명세서에 없어서 실패 블록을 추가했다.

### 6일차: AI 워커와 API 연결
- 팀장님이 `worker/model.py`의 `predict()`를 정해진 이름과 입출력으로 먼저 올려 주셔서, 나머지는 그 함수를 **호출만** 하는 방식으로 API를 먼저 작성했다. AI 모델 자체는 아래 AI 모델 서빙 파트에서 설명한다.
- AI 폐렴 예측(`POST /api/v1/medical-records/{record_id}/predictions`) 흐름: 진료기록 확인(없으면 404) → 같은 진료기록에 같은 모델로 저장된 결과가 있으면 AI를 다시 돌리지 않고 200으로 응답 → 진료기록의 X-Ray 파일 경로 확인(없으면 404) → `predict()` 호출 → 결과 저장 후 201로 응답.
- 오래 걸리는 추론은 별도 스레드에서 실행해 서버가 멈추지 않게 했고, 히트맵을 만들지 못하면 `heatmap_url`을 `null`로 둔다.
- DB에 `(record_id, ai_model)` 유니크 제약을 걸어 두었고(DB 마이그레이션), 같은 요청이 동시에 들어오면 먼저 저장된 결과를 200으로 돌려줘서 중복 저장을 막는다.

### AI 모델 서빙
- 모델 선정: 부트캠프 인공지능 트랙 DACON 흉부 X-Ray 폐렴 분류 해커톤에서 만든 모델 중 **ResNet18(`E8_lung_crop`)** 단독 모델을 사용했다.
    - 앙상블보다 Recall은 조금 낮지만, 가볍고 Grad-CAM 히트맵 코드가 이미 있어 3초 기준을 맞추기 용이하다고 판단했다.
- 예측 흐름
    1. 흑백 변환 → 비율 유지 224×224
    2. 테두리 검은 띠 제거
    3. torchxrayvision으로 폐 위치 찾기(폐를 못 찾으면 사진 전체 사용)
    4. 폐 영역 + 8% 여백만 잘라 224×224 사이즈 맞추기
    5. ResNet18로 폐렴 확률 계산 → 0.5 이상이면 폐렴, confidence는 판정한 쪽(폐렴 or 정상)의 확률 × 100(퍼센트로 표현)
    6. Grad-CAM 히트맵 저장 (실패해도 예측 결과는 반환)
- 해커톤용에서 서버용으로 변경한 점
    - 서버 시작 시(lifespan) 모델을 한 번만 불러오고, 그때 가중치만 안전하게 읽었다(`weights_only=True`).
    - 동시 요청이 들어와도 히트맵 계산이 섞이지 않도록 예측은 한 번에 하나씩 처리했다.
    - 같은 진료기록 + 같은 모델의 결과가 있으면 다시 추론하지 않고 저장된 결과를 반환했다(새로 예측하면 201, 저장 결과를 불러오면 200).
    - 가중치 파일은 GitHub에 올리지 않고 드라이브로 공유해, 각자 `worker/models/`에 저장했다.
- 결과
    - NFR-PRED-001: 검증 1,044장 기준 Recall 0.9742, Accuracy 0.9732 → 최소 기준(Recall 0.90), 보조 기준(Accuracy 0.80)을 모두 만족했다.
    - NFR-PRED-002: 사진 1장 예측(전처리 + 폐 위치 찾기 + 예측 + 히트맵 저장까지) 첫 예측 0.80초, 이후 예측 평균 0.60초로 3초 기준을 통과했다.
    - 검증 사진 중 무작위로 정상 3장, 폐렴 3장을 선택해 해커톤 노트북(ipynb) 결과와 서버 결과를 비교해보니 판정과 confidence가 완전히 동일하게 나오는 것을 확인했다.

## 7. 화면 연결 및 실행 확인
- 제공받은 프론트엔드 템플릿(`static/`)을 FastAPI 백엔드와 연결해 웹 화면에서 주요 기능을 확인했다. 템플릿과 실제 API의 차이를 해결하기 위해 로그인 경로(`/users/*` → `/auth/*`), 필드명(`phone` → `phone_number`), 성별(`M/F`)·부서(`develop/medical/research`) 값을 명세서에 맞게 수정했다.
- X-Ray·히트맵 이미지의 파일 경로를 처리하고 조회 기능을 연동했다. 이미지는 공개 폴더가 아닌 `private_uploads/`에 저장되므로, 로그인한 직원만 인증 토큰을 통해 이미지를 받을 수 있도록 X-Ray·히트맵 조회 API 2개를 추가했다.
  - `GET /api/v1/medical-records/{record_id}/xray-image`
  - `GET /api/v1/medical-records/{record_id}/heatmap`
- 화면 동작에 필요한 응답 필드 `id`(본인 권한 변경 방지), `role`(회원 권한 표시), `patient_id`(환자 상세 화면으로 돌아가기)를 팀 회의에서 결정해 추가하고, 명세서 비고에 추가 이유를 기록했다.
- 팀원 4명이 API 20개를 분담해 실제 화면에서 성공·실패 시나리오를 테스트했다. 브라우저 자체의 입력 검증과 백엔드 API의 오류 응답을 구분하여 동작을 확인했다.
- 각자 담당한 API의 테스트 결과와 성공·실패 화면을 캡처해 `docs/7일차_앱_실행화면.md`에 정리했다.

- 실행 화면: [7일차 앱 실행화면](docs/7일차_앱_실행화면.md)
